# VALIDATION FRAMEWORK — Velmore (working scorecard)

A **working scorecard**, not a standard and not documentation. Its only job: **capture
evidence while we actually build Velmore** — what genuinely worked, what didn't, which
Website OS parts earned their place and which didn't.

- **Velmore is the validation project for Website OS v2.4.0** (now frozen).
- This file **does not modify the OS** and must never become an OS standard.
- It feeds the **Continuous Learning Loop** (`SYSTEM/03` §4 · `PIPELINE/learning-loop.md`).
  Candidates recorded here only graduate into the OS **after** the project proves them out
  → they become OS `LEARNINGS.md` entries, and drive **Website OS v2.5.0** when the time comes.
- **How to use it:** at the close of each major phase, fill that phase's table honestly.
  Keep entries terse and evidence-based (what happened, not opinions). Distinguish
  *"available but not needed"* from *"used and unhelpful"* — only the second is a signal to cut.

> Scope guard: the OS stays frozen until Velmore is completed and evaluated. Nothing here
> changes the OS mid-project; it only records evidence.

## Phase 1–3 — Research, Discovery & Blueprint  ·  status: ✅ done (seeded)

| Prompt | Evidence / notes |
|---|---|
| Worked really well | The audit surfaced serious, specific issues fast (demo content live, two domains, two booking engines, NAP fragmentation). Parallel research agents (business/competitor/SEO) gave depth quickly. The **Blocking Question** + **Revenue-first** framing produced a sharp positioning wedge (publish capacities + pricing the market hides). Verified/client-stated/assumed tagging kept us honest. |
| Slowed us down | The two-site brand fragmentation made discovery ambiguous. A large share of "facts" were unverifiable → a long `03-CLIENT-INFO-REQUIRED` list that now blocks Gate 1. |
| OS docs actually used | `DISCOVERY-CHECKLIST`, `BUSINESS-RESEARCH`, `COMPETITOR-RESEARCH`, `SEO-RESEARCH`, `COPYWRITING`, `schemas/client-brief`, `DESIGN-LANGUAGE/00` + `01-HERO-SYSTEM`, `SYSTEM/04-MARKETING-ENGINE`, `SYSTEM/03-BUSINESS-INTELLIGENCE`, `gates.md` (Gate 1), handover templates. |
| OS docs NOT used (yet) | `01-DESIGN-TOKENS`, `02-TECH-STACK`, `07-PERFORMANCE` (Phase 4–6 — not reached, not a signal). No hospitality `PLAYBOOK` exists — its absence was felt. |
| Standards that saved time | Client-brief schema + Design Language gave a ready structure; Marketing Engine's revenue matrix + landing-page thinking shaped the sitemap directly. |
| Standards that felt unnecessary | *(none yet — reassess once building)* |
| Discovery Qs that produced value | "What genuinely makes them different?" and the capacity/price gap questions drove the whole strategy. Reputation/review-theme mining exposed real objections (event food, maintenance). |
| Discovery Qs to remove | *(TBD — none flagged yet)* |
| Best client-outcome drivers | The honest gap map + the "designed from inside" pull toward specificity over cliché. |
| Needs refinement post-launch | *(TBD)* |
| Unexpected lessons | A client can be running **two live sites under two brand names** — discovery must check for duplicate/parallel domains early. Demo/theme placeholder content can sit **live and indexed** for years. |
| Promote to OS (candidate — after validation) | (a) A **hospitality PLAYBOOK** (default hero archetype, capacity-table pattern, OTA vs owned-booking strategy). (b) A discovery step: **"check for duplicate/parallel domains & brand variants."** (c) The **capacity + price-transparency wedge** as a reusable hospitality pattern. |
